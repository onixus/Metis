# ADR-0005: единая сборка runtime и поставка рабочего контура

Дата: 2026-09-22. Статус: принято для пилота. Связанные требования: NF-R06, NF-O01, NF-S01, CM-03, PR-05.

## Контекст

API в памяти собирает обработчики доменных событий, но отдельный PostgreSQL-воркер их не регистрирует. В образе API отсутствует браузерный интерфейс. Настройки compliance живут в экземпляре сервиса. Получается несколько несовместимых вариантов одного продукта, при этом in-process acceptance не проверяет поставляемый runtime.

## Решение

- Сборку доменов и регистрацию обработчиков использовать совместно в API и отдельном воркере. Воркер не требует OIDC и не поднимает публичный HTTP API.
- Известные события без потребителя подтверждать только по явному списку; неизвестные события отправлять в повтор/DLQ. Отсутствующий адаптер не является успешным выполнением команды.
- Поставлять статическую React SPA с API на одном origin. Публичная конфигурация браузера содержит только режим входа и публичные параметры OIDC, без секретов. API-маршруты не подменяются SPA fallback.
- Настройки compliance читать из Store, с прежними значениями по умолчанию только при отсутствии сохранённой настройки. Добавить таблицу новой миграцией. Ошибку чтения БД не заменять значениями по умолчанию.
- Основной сценарий PM собрать на существующих доменных операциях, сохраняя API авторитетным источником прав. При смене сессии сбрасывать кеш запросов и мутаций.

## Последствия

Пилот имеет одинаковое поведение в памяти и на PostgreSQL, а restart не меняет расчёт стоимости подтверждения. Наличие этих изменений не доказывает SLO, PITR, коммерческое лицензирование или готовность финансового модуля. Атомарность и актуальность графа требуют отдельной проверки на PostgreSQL и не выводятся из зелёных тестов в памяти.

Новых библиотек и изменений лицензирования нет.
