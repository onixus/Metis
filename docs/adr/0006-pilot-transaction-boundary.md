# ADR-0006: согласованность пилота на PostgreSQL

Дата: 2026-09-22. Статус: принято для пилота. Требования: NF-R06, NF-S01, NF-S05, PG-05, PG-07, PG-08. Развивает ADR-0002.

## Контекст

Доменные сервисы последовательно вызывали Store и Publisher без общей транзакции. Кеш графа загружался при старте процесса. Несколько API/worker процессов могли проверять циклы и права по устаревшему графу; ошибка публикации оставляла сохранённые данные, а HTTP уже мог ответить успехом до подтверждения БД.

## Решение

В application runtime PostgreSQL вводится единая граница операции: mutex экземпляра приложения → транзакция → общий advisory transaction lock → загрузка графа из этой транзакции → доменная операция → commit. Контекст транзакции используют все PG-хранилища, аудит и outbox. Ответ API буферизуется до commit; ошибка HTTP откатывает операцию. После отката граф перезагружается из БД. Отказы аутентификации сохраняются отдельной транзакцией после отката, без токена и непроверенных claims.

Воркеры берут тот же lock до захвата outbox-строк, чтобы порядок блокировок совпадал с API. Между сообщениями граф перечитывается с учётом отката savepoint. Scheduler и webhook используют ту же границу; прямые вызовы доменных сервисов за пределами runtime остаются ответственностью вызывающей стороны.

## Альтернативы

- Только HTTP-транзакция без перезагрузки графа оставляет отменённые изменения в памяти.
- Только один API экземпляр не устраняет конкуренцию с отдельным worker.
- Версионированный граф, optimistic concurrency и блокировки по агрегатам предпочтительны для большой нагрузки, но требуют отдельного нагрузочного и property-based подтверждения.

## Последствия

Пилот получает простой проверяемый порядок записей и согласованный граф между процессами. Цена — сериализация операций и полная загрузка графа, а вызовы внешних интеграций в обработчиках увеличивают время удержания lock. Это не доказательство NF-P01…P06/HA. До коммерческого масштабирования необходимы метрики времени ожидания, нагрузочный профиль и замена общей блокировки (вопрос 30). Ответ API ограничен 32 MiB; превышение не приводит к частичному commit.

Применённые миграции не меняются, новые зависимости не вводятся.
