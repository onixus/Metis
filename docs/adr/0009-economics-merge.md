# ADR 0009: совместимость двух финансовых моделей при объединении веток

Статус: принято, 2026-09-22.

В main появились настраиваемые поля, метрики и сценарии; ветка пилота добавила неизменяемые книги периодов с PostgreSQL, аудитом и коннекторами. Их типы Service, Store и Snapshot несовместимы. Замена одной реализации другой потеряет опубликованные API и данные стенда.

Сохраняем economics как журнал периодов, а конструктор main переносим в economics/modeling. Публичные HTTP пути обеих моделей сохраняются. Композиция приложения явно держит два сервиса. Существующий конструктор сохраняет ограничение main: его данные пока в памяти; он не является источником сохранённых книг периодов. Автоматический перенос значений между моделями не выполняется. Объединение хранилищ требует отдельной миграции и согласования семантики полей.

Compliance сохраняет scoped интерфейс настроек. Коллизии миграций двух веток разрешаются отдельной совместимой миграцией, существующие данные не удаляются.

Миграции compliance main 00003/00004 сохранены без изменений в `db/compliance/history/main`. Активная последовательность 00001, 00002, 00003 (пилот), 00005 поддерживает обе истории goose: main уже выполнил 3/4, пилот — 3, новая база начинает с 1. Версия 5 добавляет отсутствующие components и совместимый singleton к настройкам main; исходные id/updated_at сохраняются. История goose не переписывается. Проверка `TestCM03_CM08_MergeDatabaseLineages` создаёт обе исходные базы, записывает настройки, обновляет и повторяет миграцию. Возврат приложения на предыдущую версию сохраняет старые колонки; откат схемы через этот исторический разрыв не поддерживается.

Операция импорта конструктора переименована в OpenAPI в `importModelFinanceFile` для уникальности operationId; HTTP URL и тело запроса сохранены. Финансовые политики конструктора выделены в ActionReadModelFinance/ActionWriteModelFinance, чтобы не менять политику finance+full+private журнала периодов.
