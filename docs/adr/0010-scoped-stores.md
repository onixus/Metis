# ADR-0010: явные полномочия на границе хранилищ

Дата: 2026-10-10. Статус: принято для реализации issue #18.

## Контекст

AD-02, NF-S01 и инвариант 3 требуют запрета по умолчанию при прямом вызове
репозитория. Проверки только в Service недостаточны. Проверять лишь новый
product_id недостаточно: upsert может перезаписать чужую запись с известным ID.

## Решение

Каждая операция продуктового Store получает authz.Scope после context.Context.
Сервис передаёт полномочия вызывающего. Реализации проверяют действие и продукт,
списки фильтруются по доступным продуктам, явный чужой product_id отклоняется.
При записи принадлежность существующей записи неизменяема: проверка и запись
атомарны под mutex в памяти и предикатом ON CONFLICT в PostgreSQL.

Полная загрузка графа для расчётов выполняется с отдельными служебными
полномочиями, создаваемыми identityaccess. Их нельзя брать из пользовательского
контекста или передавать пользовательским операциям записи. Общий кеш не должен
становиться частичным от первого ограниченного пользователя.

Межпродуктовые контракты сохраняют действующую семантику: право записи одной
стороны и стратегическое чтение другой; подмена сторон существующего ID
запрещена. Глобальные настройки и обработка событий используют отдельные явные
проверки существующих административных/служебных ролей.

Аудит, журнал доказательств и outbox используют тот же обязательный Scope.
Полная цепочка и очередь доступны только служебной роли с private ко всем
продуктам и внутренней аудиторией. Logger, Publisher и Worker передают эти
полномочия явно; пользовательские сервисы сохраняют авторизацию до обращения
к инфраструктурному протоколу. Ограниченный служебный scope и роль admin
без service не дают прямого доступа к общей цепочке или очереди.

## Последствия

Изменяются внутренние Go-интерфейсы и их вызовы, HTTP API сохраняется.
Новые зависимости не нужны. SQL генерируется из queries; применённые миграции
не переписываются. Отказные тесты вызывают реализации напрямую; архитектурный
тест контролирует сигнатуры Store. Проверка нулевого Scope сама по себе не
считается защитой от доступа к чужому продукту.

Внутренние производные операции (rollup, распространение дат и пересчёт
ценности сигнала) используют служебный Scope только после проверки исходного
действия пользователя; данные для записи формирует домен. При вычислении
финансового агрегата источник формул получает внутренний Scope чтения с теми
же продуктами и без ролей записи. Сырые строки Store.Facts требуют FinanceFull;
публичное Explain сохраняет эту же проверку. Область продуктов при вычислении
никогда не расширяется, даже если формула убирает измерение продукта.

Реализации в памяти копируют входные и выходные коллекции: ссылка на map/slice
не должна позволять читателю изменять сохранённые данные без повторной проверки
Scope. Общий kernel.CloneValue сохраняет типы (включая int64 и decimal) и
копирует экспортируемые поля доменных значений; скрытые поля неизменяемых
значений time.Time/decimal сохраняются. JSON round-trip не используется, чтобы
не превращать целые числа в float64 внутри map[string]any.

Обязательный govulncheck выявил уязвимости существующего toolchain и HTTP/2.
Используются исправленные Go 1.27.2 и golang.org/x/net v0.60.0 (прежняя
BSD-3-Clause зависимость, сопровождаемая командой Go). Это обновление
существующей зависимости; новые исключения security gate не вводятся.

Архитектурный тест проверяет все Store, включая инфраструктурные, без
исключений. Отказные тесты проверяют все публичные операции реализаций с
нулевым scope до I/O, а инфраструктуру также с ограниченным служебным,
стратегическим, внешним и обычным административным scope.
