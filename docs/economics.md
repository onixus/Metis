# Экономика: единый расчёт, история и источники

Текущий пользовательский путь: выбрать книгу и месяц → загрузить CSV/XLSX → проверить строки и сверку → сохранить версию → настроить аллокацию → при необходимости объединить прежнюю модель с книгой → работать с общими полями/формулами и сценариями → закрыть период. Данные стенда синтетические. Это управленческий P&L, без валютной конвертации, налоговой модели и регламентированной бухгалтерской отчётности.

## Книги и финансовая арифметика

Книга имеет владельца-продукт и может содержать строки нескольких продуктов портфеля. Месяц `YYYY-MM`, валюта одна; деньги — int64 в минорных единицах. Выручка, ФОТ, прямые затраты, маркетинг, хаб, сертификация и поддержка веток доступны по продукту и команде. Исходные суммы внешней системы не редактируются формой правил.

Прямые затраты = ФОТ + прямые расходы + маркетинг + сертификация + поддержка веток; прямая прибыль = выручка − прямые затраты; прибыль с хабом = прямая прибыль − распределённый хаб. Доли суммируются в1; largest-remainder с tie-break по UUID сохраняет каждую минорную единицу. BundleID отмечает уже распределяемую выручку бандла. В API книги `revenue` включает её, `bundle_revenue` показывает включённую часть. Legacy PnL сохраняет свой контракт: `revenue` без бандла + `bundle_revenue` = общая выручка; повторной аллокации после объединения нет.

Каждая запись — новая неизменяемая версия. `expected_version` защищает конкурентную запись. Закрытие тоже создаёт версию; последующее исправление данных требует явного пересчёта. Сценарий не меняет факт.

## Повторный импорт

Обычный импорт заменяет строки и сохраняет определения, но сбрасывает правила/ручные значения новых строк. Флаг сохранения правил включает строгую сверку до записи. Совпадение определяется уникальными source file/sheet и бизнес-измерениями строки; сумма, headcount, номер строки и hash файла не являются идентичностью. Сортировка и исправленная сумма сохраняют ID/доли/manual Values. Неоднозначность и исчезновение настроенной внешней строки запрещают весь импорт. Служебные ручные строки общего конструктора сохраняются отдельно и не выдаются за входной файл.

Предпросмотр показывает добавления/изменения/удаления и суммы статей до/после точными десятичными строками минорных единиц. Сохранение использует версию именно этого предпросмотра. Файл/маппинг и режим нельзя менять во время незавершённого предпросмотра/записи.

## Объединение исторических моделей

В «Объединении истории» выбранная книга становится единственным текущим источником месяца. Операция требует PostgreSQL, finance/full и доступа ко всем продуктам. Это явное переключение, а не сложение независимых денег.

Предпросмотр перечисляет исходный и канонический P&L, отсутствующие в книге отдельные поля модели, все архивируемые версии и отображение определений. Пользователь подтверждает выбор книги по digest. Перед атомарной записью проверяются обе версии, источники, типы/валюты, компиляция и возможность расчёта перенесённых формул. Изменившийся план получает409 без частичной миграции. Повтор подтверждённого digest идемпотентен.

Сохраняются все исходные book snapshots, model batches (включая rejected и ошибки), facts, версии полей/метрик/правил, команды/доли и закрытое состояние. Архив доступен JSON через API/интерфейс. Новые определения книги получают детерминированный namespace, с сохранением оригинальных ключей и типов в истории. Условия остаются ленивыми; `div16`, `round_minor`, `min_pair`, `max_pair` сохраняют арифметику прежнего DSL. Коллизии семантической истории и несовместимые типы/валюты блокируют план.

После применения текущие model Facts/P&L/командные отчёты и формулы читают книгу через публичные scoped-порты. Изменение книги видно сразу; собственный импорт model facts/аллокаций за этот месяц запрещён, включая старые raw DB write-пути. Показатели книги редактируются в общем конструкторе, отдельный редактор определений книги отключён. Общие manual-поля пишут в эту же книгу; новый legacy batch не создаётся. Сохраняются соседние product/team/item группы и исходные внешние суммы. Старые Team.ID продолжают работать при совпадении ключа команды.

Явно выбранные исходные версии книги из архива объединения, ставшие историческими, сохраняют расчёт со своими оригинальными определениями. Текущая версия и все новые версии после объединения исполняют показатели общего registry: сохранение, сверка импорта и проекция входов не исполняют устаревший локальный DSL. Выбор post-binding версии закрепляет входы; расчёт использует действующие на период общие формулы и показывает их в lineage. Это новый расчёт закреплённых данных, а не immutable результат отчёта. Перед сохранением книги текущие общие показатели проверяются на candidate snapshot; ошибка не создаёт новую версию. Отдельный запуск произвольной общей формулы на original версии также является новым расчётом с закреплённым входом. Исторический `data_version` запроса model facts продолжает обозначать первоначальную modeling историю. В `FactRow` ненулевой `book_product_id` указывает другой источник: `batch_id` — snapshot ID книги, `data_version` — её версия; отсутствие/нулевой UUID обозначает исходную модель.

Независимые старые поля, которых нет в выбранной книге, архивируются и явно перечисляются в плане. Их деньги не прибавляются скрыто. Опубликованное manual-поле можно затем явно заполнить в общем конструкторе. Импортные поля сохраняют read-only владение.

## Прямые formula-порты

Доступны `worklogs()`, `crm_revenue()`, `headcount()`. Они используют активный product/team/month; двухаргументная форма, например `headcount("product", "*")`, явно изменяет одно измерение. Произвольные URL, SQL, shell и сетевой код в формулах отсутствуют. Все проверки используют исходный Scope пользователя.

- `worklogs()` — целые секунды из полного набора актуальных delivery issues и tracker worklogs за UTC месяц. Требуются свежая полная проекция и deployment-owned карта opaque author→team. Неизвестный автор, конфликт issue ownership, неполный ответ и дробная секунда запрещают расчёт. Авторы и индивидуальные списания в provenance не возвращаются.
- `crm_revenue()` — целые минорные единицы выигранных сделок, отнесённых по ClosedDate к месяцу и по единственному первичному ProductKey к продукту. Attach-list Products не дублирует деньги. Нужны полный ответ, корректная дата и валюта модели. Неавторитетный командный срез отклоняется. Это управленческая выручка выигранных сделок, не бухгалтерское признание выручки.
- `headcount()` — целые люди по доверенным payroll team aggregates выбранной книги. Повторные строки одной команды должны иметь согласованную численность. В продукте учитывается участвующая команда целиком; портфель дедуплицирует одну команду, а не складывает её копии по продуктам. Это people, а не FTE. Неизвестное покрытие не превращается в0.

Книгу источников задаёт `METIS_FORMULA_BOOK_PRODUCT_ID` либо связь объединённого месяца. Карта worklogs: `METIS_WORKLOG_TEAMS_FILE` с JSON `{"author_team":{"opaque-key":"team-key"}}`; секретов/реальных данных в репозитории нет. CRM/Delivery подключаются существующими provider-настройками. Без настроенного источника функция возвращает ошибку, а не демонстрационный результат.

Открытый месяц читает реальный адаптер и сохраняет immutable aggregate snapshot в economics.formula_sources. Неизменившееся содержимое не создаёт лишних версий. Портфельные CRM/worklog расчёты получают один полный внешний ответ. В рамках расчёта повторный source+slice закреплён; базовая и сценарная стороны используют тот же снимок. В Explain присутствуют snapshot ID, captured_value, время, единицы и aggregate provenance без персональных данных.

Закрытый месяц читает сохранённый снимок без обращения к внешнему источнику. Закрытие книги предварительно проверяет и фиксирует зависимости текущего общего отчёта, пока период открыт; ошибка источника откатывает закрытие и уже подготовленные captures/audit. У никогда не зафиксированного источника закрытого месяца результат unavailable.

## Общий конструктор и сценарии

Поля money/number/percent/date/reference имеют версии и дату действия. Ручной расчётный ввод реализован для числовых типов; нечисловые исходные атрибуты сохраняются в книге/истории. Числа передаются строками без преобразования в JavaScript Number. Manual money — целые int64 minor units. Каноническая книга сохраняет свой точный формат: до48 символов decimal и12 дробных знаков; непредставимое значение отклоняется без округления. Новый canonical key ограничен64 символами; существующий namespaced key отображается обратно в исходный ключ.

Формулы используют `field("key")`, `metric("key")`, арифметику, условия, dimension aggregates и прямые порты. Циклы запрещены. Повторное поле с тем же фильтром читается один раз; Explain раскрывает только исполненные ветви и реальные фильтры. Тип денежного перенесённого показателя сохраняется, результат обязан быть int64 minor units; для явного округления используется `round_minor`.

Сохраняемые сценарии меняют field либо source (взаимоисключающие варианты), product/team/month slice, бюджетную дельту и явный сдвиг capacity дней. Fact и планы не изменяются. Результат включает baseline/scenario P&L, значения и объяснения на одном source snapshot. Частичная подмена неаддитивного агрегата отклоняется. Виртуальный budget input учитывается при оценке финансирования треков.

Влияние на обязательства сравнивает реальную связанную дату поставки и дату со сдвигом со сроком. Источник: явно заданное продление → релиз → фича/её roadmap. Неоднозначный/отсутствующий/завершённый без actual date план отмечается unknown. Capacity задаётся пользователем днями, причинная модель загрузки команды не выводится автоматически.

Закрытые определения/правила нельзя менять задним числом; будущие версии разрешены. Для book-bound месяца закрытие выполняется только в книге. Переоткрытие/смена канонического владельца и бизнес-откат на старый бинарник, не понимающий binding, не являются поддержанными операциями этой миграции. Исходные данные сохранены; схемы обновляются только новыми миграциями.

## Доступ, лимиты и проверка

Книга требует finance/full и прав на владельца, исходные и целевые продукты. Прежний агрегированный modeling доступ сохраняется для необъединённых периодов; при binding права книги не расширяются внутренним calculation scope. Нулевой Scope запрещает всё. Финансовый аудит fail-closed; PostgreSQL commit/rollback охватывает данные, audit и outbox. Роль приложения имеет SELECT/INSERT на финансовую историю, UPDATE/DELETE запрещены.

Ограничения исполнимости явные: книга10000 строк/64 поля; миграция128 book revisions и32MiB архива с ранней проверкой накопленного размера; CEL8192 байта; bounded decimal на входах и результатах; до128 разных direct source slices. Полные исходные ответы CRM/worklogs, team mapping и книга/headcount фиксируются до проекции срезов на одну операцию с изоляцией по provider и исходному Scope; общий кеш удерживает не более128 capture keys и32MiB сериализованных исходных данных. Новая операция перечитывает открытые источники; ошибка/отмена или превышение бюджета не возвращают частичный источник. Explain ограничен50000 строками,4096 узлами,16384 единицами происхождения и полной глубиной6. Превышение даёт ошибку без усечения или частичного применения; для крупного отчёта выбирается меньший срез. Это ограничения безопасности исполнения, не измеренные нагрузочные SLO.
