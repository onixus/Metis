# Экономика: работа и проверяемые границы

Итерация 13. Сценарий для финансового владельца: выбрать книгу и месяц → загрузить CSV/XLSX → проверить строки → сохранить версию → настроить доли/показатели → проверить прямой и нагруженный P&L → закрыть период. Сценарии меняют входы выбранного продукта в памяти, фактическую версию не изменяют.

## Финансовая книга

Книга принадлежит одному продукту, но может включать строки нескольких продуктов портфеля. Период — календарный месяц `YYYY-MM`, валюта задаётся явно и не меняется внутри книги/месяца. Строки содержат выручку, ФОТ, прямые затраты, маркетинг, нагрузку хаба, сертификацию и поддержку веток. Суммы неотрицательные; конвертация, налоговая модель и сторно не реализованы. Это управленческий P&L, а не регламентированный бухгалтерский отчёт.

Прямые затраты — ФОТ + прямые расходы + маркетинг + сертификация + поддержка веток. Прямая прибыль = выручка − прямые затраты. Прибыль с хабом = прямая прибыль − распределённые затраты хаба. Выручка бандла и затраты распределяются явно заданными долями строк; доли в сумме равны 1. Остатки минорных единиц распределяются по наибольшей дробной части, при равенстве — по UUID продукта. Сумма сохраняется точно, переполнение отклоняется.

Распределение, поля и формулы входят в неизменяемую версию. История доступна в селекторе версии; сравнение показывает изменение прибыли в том же продуктовом/командном срезе. Конкурентные изменения с устаревшим `expected_version` получают 409. Закрытие создаёт ещё одну версию, последующие изменения требуют явного пересчёта; закрытый статус сохраняется.

Источник суммы доступен только для чтения. Настройка правил использует сохранённые строки и принимает только доли и значения ручных полей. Повторный ручной импорт создаёт новые строки и сохраняет определения показателей; ранее заданные доли/ручные значения не сопоставляются с новыми строками неявно. Предупреждение об этом показано до сохранения импорта.

Автозагрузка собирает все профили вне общей транзакции, затем сохраняет периоды одной PostgreSQL-транзакцией. Все источники должны покрывать одинаковый набор непустых периодов; неполный источник, изменённый закрытый период или изменённая книга с ручными правилами отменяют пакет целиком. Неизменившиеся данные не создают новых версий. Ошибка видна в журнале worker, последние данные остаются доступны. Для фонового режима используйте PostgreSQL; memory-режим предназначен для локальных тестов и не гарантирует атомарность нескольких периодов.

## Доступ

Операции требуют одновременно роли `finance`, уровня `finance=full` и доступа к владельцу книги, исходным и целевым продуктам. `admin`, `cpo`, `service` и уровень `aggregates` сами по себе доступ не дают. Так исключается восстановление ФОТ маленькой команды из разности прибыли и остальных итогов. В дальнейшем агрегированный доступ нужно расширять вместе с подавлением связанных показателей, не только колонки ФОТ.

Все чтения строк, истории, P&L, шаблонов, предпросмотр и экспорт аудируются; ошибка аудита прерывает операцию. Роль БД приложения не может обновлять/удалять финансовые версии; триггер также запрещает эти изменения. ФОТ — агрегат команды, индивидуальные зарплаты и авторы worklogs в снимок не попадают.

Синтетический HMAC-стенд:

```bash
docker compose -f deploy/compose/docker-compose.yml exec api \
  /dev-token -subject pilot-finance -roles finance -finance full
```

В OIDC токен должен содержать `roles: ["finance"]` и `finance: "full"`; realm-пример включает mapper и синтетического пользователя finance. При `METIS_SEED=true` книга EDR за сентябрь 2026 содержит синтетический P&L EDR/VM: выручка 9 млн RUB, прямые затраты 3,9 млн, хаб 0,6 млн, итоговая прибыль 4,5 млн. Данные явно демонстрационные.

## Формулы и детализация

Типы: деньги, число, процент, дата, справочник. Числовые ручные поля агрегируются по выбранным строкам; денежные поля также распределяются с сохранением минорных единиц. Даты/справочники сохраняются как атрибуты; они не являются числовыми операндами. Формулы используют статьи, `direct_total`, `direct_profit`, `loaded_profit` и ключи других числовых полей. Доступны арифметика, `min`, `max`, `ifgt(a,b,yes,no)`, `ifge`, `ifeq`; вычисляется только выбранная ветка условия.

Пример маржинальности: `ifgt(revenue,0,loaded_profit/revenue*100,0)`. Произвольный код, сетевые запросы и обращение к чужим полям недоступны. Циклы и неизвестные переменные запрещены. До 64 полей, 10 000 строк, 500 000 единиц стоимости расчёта; формулы и числа ограничены по размеру. Отчёт раскрывает зависимости показателей и исходные строки/хеши.

Срезы продукта и команды фильтруют строки до расчёта; команда × продукт отражает распределённые затраты. Привязки `feature_id`, `certification_track_id`, `branch` дают инвестиции и соответствующую выручку. Продукты, фичи и треки проверяются через публичные интерфейсы модулей.

В браузере суммы за пределами безопасного целого JavaScript не отображаются как точные: используется CSV с серверными int64. Основные единицы в интерфейсе поддержаны для RUB/USD/EUR/GBP/CNY; остальные валюты показаны в минорных единицах. Расчёт не использует валютную конвертацию.

## Jira worklogs

Настройте `METIS_WORKLOG_TEAMS_FILE` на JSON `{"author_team":{"opaque-jira-key":"team-key"}}` (без реальных персональных данных в репозитории). Свяжите фичи с эпиками и дождитесь успешной сверки. В «Правила и показатели» действие «Распределить по Jira worklogs» создаёт новую версию с долями команд за месяц UTC.

Используются продукты, уже объявленные строками/долями книги, и задачи их текущих проекций эпиков, включая сам эпик. Администратор должен подтвердить полноту этого охвата для периода: историческое восстановление задач, удалённых или перенесённых из эпика до синхронизации, не реализовано. Неизвестный автор, устаревшая/неполная проекция, конфликт принадлежности задачи или отсутствие списаний команды запрещают пересчёт. Повторное применение заменяет доли по текущему снимку worklogs, учитывая удаление записей в этом охвате. Авторы и индивидуальные списания не возвращаются HTTP-клиенту.
