# Итерация 12 — целостный пилот управления B2B-продуктами ИБ

Дата: 2026-09-22. Основание: запрос владельца изучить реализованное и запланированное и довести сырую платформу до целостного состояния. Прочитаны ТЗ, разделы 1–6, планы 01–11, вопросы и описание этапа 2.

## Цель и проверяемый результат

Пользователь входит в поставляемое приложение, выбирает или создаёт продукт, принимает сигнал B2B-спроса, связывает его с фичей, оценивает её, помещает в roadmap и контролирует обязательства и compliance. Записи сохраняются в PostgreSQL; отдельный воркер действительно исполняет события; смена пользователя не показывает данные предыдущей сессии. Реализованное и оставшиеся условия коммерческой поставки явно разделены в документации.

## Работы

1. Зафиксировать аудит покрытия ТЗ и дорожную карту коммерческой версии в `docs/reviews/2026-09-22-product-readiness.md`. Не считать наличие пакета или имени теста доказательством полной готовности.
2. NF-R06, PG-08, RM-03, CT-03, DL-01: единая сборка рабочего outbox-воркера для памяти и PostgreSQL; явная маршрутизация событий; неизвестные события не подтверждать молча. Подключение обработчиков проверять регрессионными тестами.
3. SG-01, SG-03, SG-05, PG-02, PR-01, RM-01: замкнуть пользовательский сценарий через существующий OpenAPI — ручной сигнал и triage, новая фича существующего продукта, ввод оценки и создание элемента roadmap. NF-S01: очищать кеши данных при смене сессии; показывать действия с учётом ролей.
4. CM-03, CM-06, PR-05: хранить настройки compliance в общем Store и PostgreSQL новой миграцией, убрать потерю настроек при рестарте (вопрос 25); проверить отказ при недостаточных правах и сохранение после пересоздания сервиса.
5. NF-O01, NF-M04, AD-01: упаковать web вместе с API, обеспечить SPA-навигацию и документированный вход на стенд; согласовать runtime-конфигурацию браузера, Compose и Helm. Добавить воспроизводимые команды и проверку generated code.
6. Проверить атомарность доменных записей/событий и актуальность графа между процессами. Исправлять как единый согласованный механизм с тестами отката/межпроцессных изменений, а не только оборачивать HTTP без восстановления кеша.
7. Выполнить Go tests с `-race`, frontend lint/typecheck/build, доступные интеграционные и security checks. Добавить проверку сквозного нового сценария. Обновить README, вопросы, описание PR с реальным объёмом проверки и авторством.

## Ограничения и решения

Новые внешние зависимости не требуются. API расширяется только через OpenAPI и генерацию. Применённые миграции не изменяются. Синтетические портфели сохраняются. Сеть ограничена реестрами пакетов; внешняя публикация и создание GitHub PR не выполняются в рамках этого ограничения.

Экономика этапа 3, подтверждённая промышленная эксплуатация, выбранные владельцем отечественные адаптеры и изолированный LLM этапа 5 оцениваются отдельно: они не становятся готовыми от наличия экранов. До ответа владельца приоритет — целостный пилот; решения, зависящие от заказчика и поставщиков, фиксируются в вопросах.
