# Итерация28 — прямые источники финансовых формул

Основание: запрос владельца завершить Экономику; EC-09/10/11/13, DL-05, NF-S02, AD-04.

До кода: приложение агрегирует только публичные портовые данные. Worklogs читаются для полного проверенного множества scoped delivery issues за UTC месяц, с явной картой opaque author→team; авторам нет места в выходном объяснении. CRM revenue строится по полному снимку выигранных сделок, ClosedDate и единственному первичному ProductKey; multi-product attach-list не дублирует сумму. Headcount берётся из авторитетной финансовой книги/месяца и согласованного team aggregate; неизвестность не превращается в ноль.

Снимки источников должны быть неизменяемыми, сохраняемыми и различать ноль от отсутствия/ошибки. Адаптеры используют узкий публичный snapshot-reader/writer; persistence координируется с основным агентом и агентом formula_sources. Функции среза работают в исходном Scope, денежные значения int64 minor units + currency, worklogs — целые секунды, headcount — целое количество людей. Никаких запросов к таблицам чужой схемы.

Проверки: синтетические полные/пустые/ошибочные/дублированные источники, собственный/чужой продукт и aggregate finance denial, currency/period/team ambiguity, отсутствие авторов/имён/сделок в публичной provenance, обновление source snapshot и сохраняемость при restart. Новых зависимостей нет; ADR0031 до реализации. Код предыдущих итераций и других чатов сохраняется.

Реализованы Sources Service/Store/MemStore/pgstore и economics00002: неизменяемые product/portfolio ревизии, source content hash, повтор без новой версии, аудит с ID/версией/hash, PostgreSQL CAS и application lock. Прямые app-адаптеры запрашивают CRM/tracker только для открытого месяца, сохраняют полный агрегат и возвращают его SnapshotID. Закрытый месяц читает сохранённую ревизию и не вызывает источник. Headcount/portfolio используют явно настроенный book или публичную canonical history binding. TeamUUID разрешается по модели Team.Key или UUID-проекции team key книги. Unit race registry/app и scoped lint0 issues прошли; реальный PostgreSQL test ожидает URL основного агента.

Финальные проверки: registry/app EC09 unit race PASS; PostgreSQL16 source restart/audit rollback/immutable trigger PASS. Coherent portfolio regression подтверждает один полный CRM Deals response и один union-issues Worklogs response для двух продуктов; книга и team mapping закреплены на время этой проекции. Секунды валидируются отдельно для каждой записи и суммируются как int64 seconds, без искусственного ограничения суммой наносекунд; большая корректная сумма и запрет дробных индивидуальных секунд покрыты тестом.

Независимое review unification выявило необходимость close-preflight: общий отчёт должен вычислиться до append закрытой версии, чтобы захватить все прямые source snapshots. В root Close добавлена предварительная проверка, отдельная PostgreSQL app-регрессия подтверждает успешное закрытие без предыдущего read и неизменность после отключения CRM; при недоступном втором источнике исходная книга остаётся открытой и частичные CRM snapshots откатываются. Тест получает отдельную runtime database, чтобы его будущие синтетические месяцы не загрязняли другие проверки. Отсутствующая/некорректная deployment-карта worklog teams выдаёт ErrUnavailable в прямом source-адаптере; прежний ручной ApplyFinanceWorklogs не изменён.

## Дополнение до canonical manual writer

По запросу основного агента закрываем оставшийся разрыв после migration: новые ручные common fields записываются в canonical book через типизированный порт (ADR0032), без legacy batches. Перед кодом выбраны обратное key mapping, нормализация только принадлежащих ручному вводу Values через точную Project аллокацию,0-cost synthetic rows с product/team/item и строгий app-only grant на проекцию одной manual schema записи. Проверки: shared formula и book metric видят значение, соседний продукт/внешняя сумма сохраняются, history/audit, закрытый период и imported-field отказ, PostgreSQL rollback.

Canonical manual writer реализован и проверен: опубликованное manual поле через прежний SetManualValue пишет только canonical book. Внутренний app grant допускает проекцию ровно одного manual определения; внешний book API такой grant не получает. Нормализация одного ручного поля сохраняет точные распределённые значения соседних продуктов и исходные внешние суммы/аллокации. Повторный setter переиспользует owned row ID, строки не растут. ModelItem проходит в ProjectedFact/FactRow и фильтрацию статьи. Незнакомая команда, source import, чужой Scope и закрытый месяц запрещены. Числа вне canonical storage48chars/12fraction отклоняются явно без округления; расширения неограниченной legacy arithmetic не было.

Фактические результаты: unit/app race canonical writer — PASS; PostgreSQL real unification→new manual value→book/model equality/no legacy batches — PASS; искусственная ошибка после реального book Append откатывает и schema projection, и value вместе с аудитом — PASS. Scoped lint0 issues. Worklog allocation пропускает app-owned0-cost manual rows; регрессия сохраняет выбранные product/team/value/rowID и nil allocations. Source-owned импортные строки с нулевой суммой не удаляются и не исключаются этим маркером. Schema/metadata additions не меняют применённые миграции.
