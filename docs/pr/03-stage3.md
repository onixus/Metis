# Pull request: этап 3 — экономика и маркетинг

## Что сделано

Итерация по плану `docs/plans/12.md`. Этап 3 лежит на модулях этапа 2: новые требования дописаны
в существующие модули, а не продублированы.

**Новые модули**

- **`internal/economics`** — экономика портфеля: настраиваемые поля с версиями (EC-08, EC-11),
  формулы показателей на cel-go с арифметикой в decimal и ограничением стоимости вычисления (EC-09),
  граф зависимостей показателей с отказом на цикле, пересчётом только затронутых и объяснением
  значения до строк импорта (EC-10), импорт XLSX по шаблону с предпросмотром, отчётом об ошибках
  по строкам, версиями данных периода, историей загрузок и загрузкой по расписанию (EC-01, EC-07),
  правила аллокации затрат хаба и атрибуции бандлов с версиями (EC-02, EC-04), P&L продукта в двух
  видах и P&L портфеля (EC-03), экономика фичи и веток (EC-05), экономика сертификации (EC-06),
  две оси детализации и матрица «команда × продукт» (EC-12), сценарии на том же движке формул
  с подменой входных значений (EC-13).
- **`internal/marketing`** — win/loss по причинам и сегментам, фичи выигранных сделок, attach rate
  (DA-04); порт CRM расширен исходом, причиной, датой закрытия и составом сделки.
- **`internal/licensing`** — ключ поставки со сроком и лимитами, подпись Ed25519, офлайн-проверка,
  льготный период, проверка лимита продуктов при создании (AD-06).
- **`internal/analytics`** — конструктор дашбордов поверх закрытого списка срезов API (DA-05, ADR-0007).
- **Порты и адаптеры**: `ports.FinanceImport` + `adapters/financexlsx` (книги XLSX и каталог для
  загрузки по расписанию), `ports.SecurityPipeline` + `adapters/securityfile` (манифесты пайплайна).

**Дописано в модули этапов 1–2**

- **`compliance`**: состав компонентов `CertifiedBaseline`, поиск затронутых сертифицированных
  версий по уязвимому компоненту с запуском регуляторных сроков (CM-08), автосбор доказательств
  из пайплайна безопасности в журнал со сцепкой хешей (CM-09), плановые затраты треков (EC-06, DA-02).
- **`commitments`**: запуск срока устранения уязвимости, идемпотентный по основанию (CM-08 → CT-02).
- **`decisions`**: измеримая часть ожидаемого эффекта и ревизия решения — ожидание против факта
  из экономики (DA-06).
- **`roadmap`**: уровень запуска и календарь запусков с учётом аудитории (RM-06).
- **`delivery`**: прогноз даты фичи методом Монте-Карло с доверительным интервалом (DL-04)
  и списания времени как база распределения затрат по продуктам и фичам (DL-05).

**API, миграции, фронтенд, приёмка**

- 33 новые операции в `api/openapi.yaml` (spec-first, серверный код и клиенты перегенерированы).
- Миграции: `compliance.baselines.components` (CM-08), `decisions.records` — измеримый эффект
  и ревизия (DA-06), `roadmap.items` — уровень и дата запуска (RM-06).
- `web`: страница «Портфель и P&L» с win/loss; дашборд compliance сделан на этапе 2.
- `TestAcceptanceStage3` — P&L продукта в двух видах сходится с контрольным расчётом, сценарий
  показывает влияние на обязательства и треки сертификации (критерий готовности этапа 3 из ТЗ 6).

## Решения вне ТЗ

- ADR-0005: зависимости `excelize` (BSD-3-Clause) и `cel-go` (Apache-2.0).
- ADR-0006: формат лицензионного ключа и офлайн-проверка.
- ADR-0007: аналитика остаётся в PostgreSQL, DA-05 — конструктор дашбордов платформы;
  ClickHouse и Superset отложены с условием пересмотра.
- Вопросы 30–40 в `docs/questions.md`.

## Как проверить

```bash
make ci
CGO_ENABLED=1 go test -race -run TestAcceptanceStage3 ./tests/e2e/
cd web && npm ci && npm run lint && npm run typecheck && npm run build
```

Контрольный расчёт приёмки: выручка EDR 10 000 000 ₽, прямые затраты 5 500 000 ₽, нагрузка хаба
SOAR 1 800 000 ₽ при доле 0,6 → прибыль 4 500 000 ₽ в прямом виде и 2 700 000 ₽ с нагрузкой.
Сценарий со сдвигом поставки на 30 дней и урезанием бюджета на 500 000 ₽ показывает одно нарушенное
обязательство и трек с нехваткой бюджета 300 000 ₽.

## Что не сделано

- PostgreSQL-хранилища модулей этапа 3 (`economics`, `analytics`, `licensing`): работают на `MemStore`,
  тогда как модули этапов 1–2 уже на PostgreSQL (вопрос №40). Схема и запросы — отдельной итерацией.
- ClickHouse и встроенный Superset (ADR-0007, вопрос №36).
- Лимит лицензии по числу пользователей не проверяется: учёта выданных доступов нет (вопрос №37).
- Состав из SBOM попадает в baseline явным вызовом после сертификации, если трек ещё не сертифицирован
  в момент сбора (вопрос №39).
- `govulncheck` сообщает о незакрытой уязвимости excelize GO-2026-6452 — исправления у поставщика нет;
  паника разбора перехватывается адаптером и превращается в ошибку валидации (вопрос №35).
- Интеграционные тесты с PostgreSQL и compose-стенд локально не запускались (Docker недоступен, вопрос №05);
  миграции этапа 3 проверены только генерацией sqlc и сборкой — прогон на стенде нужен до слияния.
