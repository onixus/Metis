# Готовность Метиды: B2B-продукты информационной безопасности

Дата: 2026-09-22. База аудита: `70b37a8`, локальный код и ТЗ; дополнено изменениями итерации 12. Проверка публичного рынка, законодательства и внешних систем в этот аудит не входит.

## Вывод

В репозитории уже существует содержательное ядро этапов 1–2, а не только макет: типизированный граф, денежный вес спроса, discovery, приоритизация, roadmap, обязательства, гейты SSDLC, baseline, решения и порты интеграций. До итерации 12 это были недостаточно связанные части: пользователь не мог пройти основной сценарий через UI, а PostgreSQL-поставка фактически не исполняла доменные события.

Итерация 12 собирает проверяемый пилот: принять потребность клиента, развить бэклог, оценить фичу, запланировать её, контролировать обязательства и сертификацию. Коммерческая поставка всего ТЗ ещё требует самостоятельных итераций, прежде всего экономики, эксплуатационного подтверждения и выбранных заказчиком интеграций.

## Исправленные блокирующие дефекты

1. `cmd/worker` создавал пустой Worker, а неизвестное событие считалось успехом. PostgreSQL-поставка теряла сообщения. Сборка доменов/handlers теперь общая; неизвестные события остаются в retry/DLQ, уведомления без потребителей перечислены явно.
2. Store.Save и Publish выполнялись раздельно. Ошибка очереди могла оставить запись или частичный сдвиг. PostgreSQL runtime теперь объединяет домен, аудит и outbox в транзакции; HTTP success отдаётся после commit.
3. Граф загружался один раз и расходился между процессами. Общая блокировка и reload до операции обеспечивают согласованность пилота; rollback/savepoint не оставляет отменённые фичи в кеше.
4. Доменный аудит игнорировал ошибки записи. Эти ошибки теперь отменяют запись; отказы аутентификации сохраняются отдельно от отклонённой транзакции.
5. Настройки compliance жили в Service, меняли расчёт после restart и раскрывали изменяемую map. Теперь настройки общие для процессов, ошибки БД не заменяются defaults, memory Store копирует map.
6. UI разрешал только часть чтений/изменений, не создание основного потока. Формы сигналов, фич, scoring и roadmap замыкают путь PM; cache другой сессии удаляется.
7. Docker-поставка не включала web, отсутствовала команда входа и runtime использовал владельца БД. API содержит SPA, публичная конфигурация не включает secrets, миграции отделены от `metis_app`.

## Что означает готовый пилот

Пилот предназначен для ограниченной внутренней группы с синтетическими либо отдельно согласованными данными. Он должен проходить сценарий с пустого продукта, проверку роли presale, отдельного PostgreSQL worker и перезапуска. Состав выполненных проверок записан в `docs/pr/03-pilot-completeness.md`; команды — в `docs/pilot-runbook.md`.

Пилот не подтверждает полноту всех M-требований ТЗ. Общий transaction lock обеспечивает корректность простым способом, но сериализует обработку; реальное выполнение NF-P/NF-R требует измерений. Store-интерфейсы старых модулей ещё полагаются на авторизацию сервиса вместо обязательного Scope — это известное отклонение от инварианта 3, а не разрешение обходить домен.

До реализации экономики нужны решения владельца: валюта/периодичность и форма контрольного расчёта, схема загрузок, правила закрытия периодов, права финансов и минимальная команда. До внешних адаптеров — конкретные системы и версии. До коммерческой приёмки — модель поставки, нагрузка, RPO/RTO-процедуры и ответственные за проверку/правообладание. Эти решения нельзя заменить неявными предположениями агента.
